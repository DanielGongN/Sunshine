# 串流断开通知

Sunshine 向上游发送 `event: "disconnected"`。`data.type` 表示分类，`data.message` 携带当前能够确定的具体原因；顶层 `message` 保留相同内容，以兼容现有消费者。

```json
{
  "event": "disconnected",
  "message": "Could not encode video frame 123 with 'h264_nvenc'",
  "data": {
    "type": 99,
    "message": "Could not encode video frame 123 with 'h264_nvenc'"
  }
}
```

## 类型约定

| 值 | 名称 | 含义 / 当前触发路径 |
| ---: | --- | --- |
| 0 | `client_requested_stop` | 客户端通过经过认证的 `/cancel` 请求明确结束串流；上游下发时按正常退出处理 |
| 1 | `force_timeout` | 挂机超时提醒，等待上游决定是否断开；上游下发此类型时使用专用终止码并保留此类型上报 |
| 2 | `standby_timeout` | 无操作超时提醒，等待上游决定是否断开；上游下发此类型时使用专用终止码并保留此类型上报 |
| 3 | `game_process_exit` | agent 上报游戏进程退出并直接向本地 Sunshine 下发；Sunshine 停止客户端，不回传同名事件 |
| 99 | `abnormal_disconnect` | Sunshine 发起的其他断流：未知原因、意图不明的对端断开、控制或启动超时、管理停止、服务退出、采集/编码/内部/协议错误等 |

以上是对外 `data.type`。代码内部仍保留 `client_reported_error`、`peer_disconnected_unknown`、`control_timeout`、`server_encoder_error` 等详细分类，以维持首次原因和恢复判断；内部数值不直接作为对外类型发送。当前没有显式客户端错误报告协议、网关致命故障监控或外部进程监控，相关内部分类不代表已实现这些报告来源。

## 归因与去重

- 会话与采集、编码上下文共享首次原因记录。错误发生时先保存类型和具体原因，再通知其他线程退出。
- 同一会话实际停止只处理一次，后续心跳超时、线程清理、服务关闭不能覆盖最初原因。
- 上游通知另外按 `client_connect` 周期统一去重：首次触发 `disconnected` 后，所有后续类型的同名通知都被抑制，直到收到新的上游 `client_connect` 事件。多个线程同时触发时也只允许一个通过；本地停止处理和原因日志不受影响。
- `1/2` 是原有业务提醒，并不表示串流已经结束，但同样占用本周期的首次上报名额。提醒上报后，本周期真正停止的 `0/99` 也不会再次上报。
- 在收到 `client_connect` 时立即重置，不等待证书校验或串流建立成功。服务端向上游发送的 `connected` 通知、确认消息及 middleware 重连均不重置。首次通知尝试沿用原有发送队列和离线丢弃规则，离线丢弃后也不会在本周期补发。
- 普通对端断开不等于用户主动退出；超时也无法证明是哪一端异常。这些情况统一上报 `99`，仅明确的客户端主动退出使用 `0`。
- 协议问题导致关闭会话也上报 `99`，但具体原因不能直接等同于服务端程序缺陷。
- 显示器切换和编码器重新初始化过程、可恢复的音频故障、单次丢包或发送错误不单独当作致命断开。
- 普通音频和已协商的麦克风通道可选：没有初始 PING 时持续等待，会话继续传输视频；稍后收到匹配 PING 后再启动对应处理。会话停止时取消等待。音频和麦克风工作线程自身的异常仅记录日志，不结束整个会话。

本地 `[stream][disconnect]` 日志包含 `session`、内部具体原因 `type` 和 `message`。通知沿用现有发送队列；中台未连接时仍会丢弃通知。

## 上游断开与客户端终止码

- 收到有效的上游 `disconnected` 时，交给控制线程停止所有正在运行的串流。`data.type=1/2` 先按相同类型及原因正常尝试上报 `disconnected`，继续遵守每周期一次规则；本周期已上报过本地超时提醒时不会重复发送。其他类型先关闭本周期的上行通知，不回传 `disconnected`。后续停止和清理不额外上报，新的 `client_connect` 才会重置名额。
- 数字 `data.type=0` 使用正常终止码 `0x80030023`；`1`（挂机超时）、`2`（无操作超时）、`3`（游戏进程退出）分别使用独立终止码 `0x8004E001`、`0x8004E002`、`0x8004E003`。其他数字类型或省略类型的有效指令继续使用普通终止码。无效的 data/type 字段会被拒绝，不停止串流，也不占用通知名额。
- 指令按到达顺序处理，首个指令选择的终止码保存在会话内。发送失败后的重试、停止和服务关闭清理都沿用这个值，并复用发送去重标志。
- `0x8004E001/0x8004E002/0x8004E003` 是私有协议扩展。本仓库的 Moonlight 控制读取代码会原样传递这些未识别的 32 位错误码；客户端是否显示专用文案取决于客户端实现。
- agent 的游戏进程监控在确定结束会话时，将原始 `message_id`、原因和 `type=3` 同时投递给上游及本地下游广播通道，Sunshine 无需等待平台回传即可收到。本地队列满时等待容量，任一路通道关闭都会独立记录错误，不阻止另一条路径投递。自愈重启失败同样下发，成功重启期间不下发；该类型也不等于 agent 服务崩溃，正常游戏退出可能进入同一路径。若平台随后回传，仍通过原有 disconnected handler 广播；已停止的会话不覆盖先前选定的客户端终止码。

## 编码器恢复

- 支持异步销毁的 NVENC 编码器发生编码、转换或初始化错误时，先销毁旧编码器并在同一会话内重建，保留控制连接和连续帧序号。新编码器从 IDR 帧开始输出。
- 同一串流会话最多允许三次重建，期间记录 `[video][encoder-recovery] attempt=N/3`，不发送正式断开通知，也不将临时错误记为首次致命原因。第四次编码器错误结束会话，以内部 `server_encoder_error` 及最终失败原因进入断开通知流程，对外类型为 `99`；是否向上游发送仍遵守上述周期去重和上游指令上报规则。
- 采集失败、不支持异步销毁的编码器失败仍立即结束会话。会话停止或采集线程已经结束时不再重试；已有致命原因和通知去重规则继续生效。
- 编码完成等待仍为 100 毫秒。此恢复机制允许短暂异常后继续串流，不能保证底层驱动故障一定能够恢复。

## 短暂断网与恢复

- 已建立控制通道连续 1 秒没有有效控制消息时进入等待恢复：释放按键、暂停音视频发送、清空网关媒体队列并静音客户端麦克风。等待阶段不发送正式断开通知。
- 在 `ping_timeout` 内收到有效控制消息可恢复；默认期限为 10 秒，每次有效消息都会刷新期限。恢复时请求 IDR，并等待关键帧后继续发送视频；暂停前正在发送的帧保持失效，不能跨恢复窗口续发。长度不合法、未经认证或不属于当前会话的数据不能延长恢复期限。
- ENet 的可靠消息超时最小值和最大值显式设置为 `ping_timeout + 2 秒`，默认 12 秒，避免其原有 5 秒条件超时抢先结束应用的恢复窗口。应用仍按自己的期限结束会话。
- 超过期限或收到 ENet 断开事件后，会话终止并保持原有分类、首次原因和去重规则。服务端立即移除失效 ENet peer 的会话映射，避免旧会话清理操作误用 ENet 重新分配的 peer。
- 支持会话 token 的直连音视频 PING 可更新同一 IP 上变化的 UDP 端口；token 必须完全匹配。网关内部目标保持不变，外部端口版本按通道维护。旧版无 token PING 不用于运行中的端口切换。
- 新启动请求遇到尚未完成的 RTSP 握手会返回状态码 `409`，客户端应稍后重试；旧握手的清理和定时器不能清除新握手，同一握手只能接受一次 ANNOUNCE。

`[control][disconnect-detail]` 记录有效控制消息空闲时长、ENet 接收/确认活动时长、最早可靠消息超时年龄、待确认消息数、最大重试次数和传输超时预算。`wire_disconnect_observed` 仅表示观察到对应 peer/session 的明文 ENet DISCONNECT 命令，不能证明用户主动退出；没有观察到也不能单独证明是本地超时。

终止后的完整自恢复需要客户端重新完成认证启动及 RTSP 握手，并使用新的会话密钥。上述服务端修改不包含客户端重连实现；真实网线插拔、QQ 通话和客户端麦克风热插拔仍需在对应客户端环境验证。
